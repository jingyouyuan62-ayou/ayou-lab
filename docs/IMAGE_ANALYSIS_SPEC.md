# Ayou-Lab 图片分析规范

状态：正式规范 v2.1（2026-10-26）

依据：`AGENTS.md`、`data/entries.json`（2026-10-26 的 83 条快照）、现有 11 条完整分析、
`archive.js`，以及项目所有者确认的 16 项分析维度。本文档不重新设计分析体系；v2.1 增加历史
分析恢复、标准映射、来源追溯和逐条验收规则。

## 0. 这份文件解决什么问题

完整分析结果过去只存在于对话里，新对话无法读取，导致格式、深度和执行顺序反复偏移。
2026-10-26 审计又确认：83 条图片中只有 11 条已有结构化 `analysis`，其余 72 条的分析仍只在
历史对话中。历史补录的目的是恢复这些判断，不是重新看图，也不是把所有图片改写成同一套结论。

从本文件生效起：

- 新增图片的完整分析以本文件为准。
- `AGENTS.md` 仍是项目级最高规则；本文件负责图片分析的具体标准。
- 对话中的临时说法不能覆盖本文件；如确需修改标准，先改本文件。
- 新图片仍需逐张看图；历史上已经分析过的图片不得为了补录而重新调用视觉模型。
- 历史补录只允许读取、摘录、映射和补齐可追溯来源；原始分析必须单独保存后才可标准化。
- 当前 11 条完整分析不因本规范升级而重写；72 条历史分析按本文第 9.1 节逐条验收后写入。
- 未获得明确授权前，不批量修改 `data/entries.json`。

## 1. 事实来源与优先级

按以下顺序取证：

1. `AGENTS.md`：项目定位、归档约定、发布流程。
2. 本文件：分析字段、深度、输出格式、检查标准。
3. `data/entries.json`：当前条目的实际字段、类型与嵌套方式。
4. 图片文件本身：颜色、构图、文字、材质等视觉事实。
5. 对话：只用于当次任务安排和用户确认的信息。

如有冲突，`AGENTS.md` 优先；其次本文件；再次数据现状。发现冲突时在报告中写明，不自行选择一套"看起来更合理"的做法。

历史补录另有一条来源优先级：

1. 当次助手最终报告中的原始分析。
2. 当次保存的结构化分析草稿或可验证报告附件。
3. 仅当前两者缺失时，才使用历史记录中明确标注为原始助理输出的可审计副本。

不能把内部推理、计划、未执行提案或后续对同一条目的概括当成原始分析。

## 2. 当前 Archive 数据结构（已核实）

`data/entries.json` 是数组，每个条目现有字段如下：

| 字段 | 类型 | 现状 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 83/83 | kebab-case，与图片文件名主干一致 |
| `title` | string | 83/83 | 1–5 个英文单词（2026-10-17 放宽） |
| `date` | string | 83/83 | `YYYY-MM-DD` |
| `source` | string | 83/83 | 只能是 `own` 或 `collected` |
| `medium` | string | 83/83 | 例：`photo`、`collage`、`illustration`、`film still`、`embroidery`、`textile` |
| `category` | string | 83/83 | `nature` / `memory` / `strange` / `color` / `dream` |
| `note` | string | 83/83 | 单句英文观察，中位数约 88 字符，最长 167 |
| `image` | string | 83/83 | `images/<filename>` |
| `accent` | string | 83/83 | `#RRGGBB`，从图片像素实测 |
| `tags` | string[] | 64/83 | 新条目使用；原始 19 条没有 |
| `echoes` | object | 74/83 | `{ "candidates": [], "confirmed": [] }` |
| `ideas` | string[] | 1/83 | 旧字段，仅 `red-tree` 使用；按确认"全部保留"，既不删除也不取代 |
| `analysis` | object | 11/83 | 完整视觉分析；新条目必须包含，历史条目按恢复流程补录 |
| `analysisSource` | object | 可选 | 仅历史恢复条目使用；记录原始对话与原文文件的来源 |

已核实的关键事实：

- 原始 19 条没有 `tags`。2026-10-26 的恢复任务只补 `analysis` 和来源元数据，不顺手补
  `tags`、标题或其他既有元数据。
- 9 条没有 `echoes`；缺失与空对象在现有数据中并存。
- `echoes.candidates` 与 `echoes.confirmed` 都是字符串数组。
- `archive.js` 只渲染 `title`、`date`、`medium`、`source`、`note`、`confirmed` echoes、`category`，并用 `accent` 作为卡片强调色。
- **历史上 `entries.json` 不存储 16 维完整分析。** 已核对全部 57 个历史版本：从未出现过
  composition、texture、spatialDepth 等分析字段，只有 `note` 单句摘要；完整分析曾只存在于
  对话报告里，这是跨对话不一致的根因。
- **从 2026-10-17 起，新条目的完整分析必须存入 `analysis` 对象。** 2026-10-26 起，
  有历史原文的旧条目通过恢复流程补录，不重新看图。

因此：完整分析存入条目的 `analysis` 对象。完整分析可以比 `note` 更细，不要求与短摘要
完全一致；`title`、`accent`、`echoes` 仍以条目顶层的现有字段为准，不在 `analysis` 中重复。

`analysis` 的键固定为：

```json
{
  "content": "string",
  "composition": "string",
  "color": "string",
  "typography": "string",
  "texture": "string",
  "material": "string",
  "spatialDepth": "string",
  "hierarchy": "string",
  "mood": "string",
  "visualStyle": "string",
  "interaction": "string",
  "dna": "string",
  "uncertainty": "string"
}
```

16 个维度与存储位置的对应关系：

- `content` … `uncertainty`（除 `title`、`accent`、`echoes` 外）→ `analysis.<field>`
- `title` → 条目顶层 `title`
- `accent` → 条目顶层 `accent`
- `echoes` → 条目顶层 `echoes.candidates` / `echoes.confirmed`
- `dna` → `analysis.dna` 写分析说明，条目顶层 `category` 只存一个主类

所有 13 个 `analysis` 字段必须是单个 string；`echoes.candidates` 与
`echoes.confirmed` 必须是 string 数组。不得因为旧分析的嵌套对象、数组或布尔值而改变正式
数据类型；映射阶段将旧值展开为等价文字，并在原文文件中保留旧结构。

历史恢复条目另加一个可选的顶层对象：

```json
{
  "analysisSource": {
    "type": "historical_chat_recovery",
    "sessionId": "01a09ed2-fcd9-7ba0-a7dd-bc85721df254",
    "messageId": "198eacd4-a553-4a56-b4a7-9b4d57d05cff",
    "timestamp": "2026-09-16T08:02:42.432Z",
    "sourceTitle": "Frozen Water",
    "originalArtifact": "docs/analysis-recovery/original/frozen-water.txt",
    "originalSha256": "64-lowercase-hex",
    "sourceFormat": "structured_json",
    "mappingVersion": "2026-10-26.v2.1"
  }
}
```

`sourceFormat` 只能是 `structured_json`、`structured_markdown` 或 `dense_prose`。
`sourceTitle` 必须记录分析当时的标题；条目后来改名时，依靠它建立历史原文与当前条目的对应。
来源对象不属于 16 个分析维度，不显示在网站上；它只用于追溯。已有 11 条的既有分析没有
历史来源对象，不反向伪造来源。

## 2.1 明确空值与待补充

不能为了填满字段而编造内容，也不能用无法审计的 `null`、空字符串或单独的 `N/A` 代替分析。
统一使用可读、可检查的明确形式：

| 情形 | 正式写法 |
| --- | --- |
| 画面没有文字 | `画面中无可读文字。` |
| 画面明确是平面，没有真实纵深 | `画面呈扁平二维排布，无可辨认的真实纵深层次。` |
| 没有与画面结构直接相关的交互方案 | `未发现与画面结构直接相关的交互方案。` |
| 材质无法确认 | `材质无法从画面确认。` |
| 历史原文未提供某个维度 | `待补充：历史原文未提供可核验的 <字段名> 内容。` |
| 没有可靠联想 | `echoes.candidates` 与 `echoes.confirmed` 使用空数组 |

“无”“没有”或“N/A”不能单独成为一个字段。字段虽然无法补全，也必须说明是画面事实还是
历史来源缺失；后一种情况会使该条处于 `needs_owner_confirmation`，不能直接写入正式资料库。

## 3. 必要分析维度

每张图片必须按以下顺序完成 16 项，不得因为批次、图片类型或"看起来差不多"而省略。

### 1. content

画面实际呈现的內容：主体、环境、可见人物或物体、状态或动作。

最低要求：用具体名词写清画面里确实存在的东西（至少 3 个可核对元素），并说明它们的关系。不要用"很美""很有氛围"代替內容。

### 2. composition

画幅方向与比例、主体位置、框取、线条方向、负空间、遮挡和视线路径。

最低要求：至少说明两组元素的空间关系，并指出哪一块区域没有成为主体（负空间或次要区域）。"居中构图"不算合格；必须说明为什么、以及它产生什么效果。

### 3. color

主色、辅助色、强调色；明度、饱和度、冷暖、对比关系；颜色造成的视觉后果。

最低要求：写出颜色角色，而不是只列颜色名；至少给出一个实测 hex（`accent` 另列，但应与本节一致）；说明颜色如何影响层级或情绪。

### 4. typography

画面中的文字、字形特征、可读性与视觉作用。

最低要求：必须明确回答"有字还是无字"。有字时说明语言、位置、清晰度与作用；看不清时写"不可辨"，不得猜内容。无字时写"画面中无可读文字"，不能省略该项。

### 5. texture

纹理特征：光滑/粗糙、清晰/模糊、颗粒、重复纹样、材质表面。

最低要求：至少覆盖两个区域或两种尺度（例如近景树皮与远景雾面），并说明纹理差异如何帮助分层。

### 6. material

画面中看得出的材质，如木、石、布、纸、水面、塑料、皮肤、金属。

最低要求：至少写两种可辨认材质；材质无法确认时，说明依据与不确定处，不能凭常识补全。

### 7. spatialDepth

前景、中景、背景的层次；遮挡、尺度、空气透视、景深和拍摄位置。

最低要求：指出至少三层，或明确说明画面是扁平/压缩的；若推断机位或高度，必须标为推测。

### 8. hierarchy

眼睛的注意力顺序，以及造成该顺序的视觉原因。

最低要求：写成有序序列（第一眼 → 第二眼 → 第三眼），每条给出原因：亮度、对比、面积、清晰度、色相或位置。只写"主体突出"不算合格。

### 9. mood

情绪与氛围，以及造成它的视觉因素。

最低要求：不能只用单个形容词。至少写成"视觉证据 → 情绪效果"的关系；并把纯联想（声音、气味、记忆）与画面证据分开。

### 10. visualStyle

视觉风格与可辨认的形式特征，如低饱和、胶片颗粒、对称、拼贴、留白、广角。

最低要求：至少两个风格特征；可以提出风格来源或滤镜猜测，但必须标为推测。

### 11. interaction

未来可以发展的互动形式。

最低要求：1–3 个，与画面结构直接相关（例如分层视差、文字悬停放大、倒影抖动），说明触发方式与视觉变化。不得写与画面无关的通用特效。

### 12. dna

与 Ayou-Lab Visual DNA 的关系：NATURE / MEMORY / STRANGE / COLOR / DREAM。

最低要求：给出主类，必要时给次类，并引用画面证据说明为什么；若五类都不能准确覆盖，明确写出，而不是硬归类。Archive 条目的 `category` 只填一个值。

### 13. accent

适合从图片提取的强调色。

最低要求：必须是实测的 `#RRGGBB`，写明取样区域（例如"檐下帷幔""水面中部""亮叶团"）。不得凭感觉填写或沿用上一张图的值。

### 14. echoes

图片引发的联想。

最低要求：严格分为两类：

- `candidates`：AI 提出、尚未被使用者确认的联想。
- `confirmed`：使用者明确说过或项目记录中已确认的地点、识别、个人记忆与关联。

不得把 AI 推测写进 `confirmed`，也不得把使用者没说过的话写成个人记忆。确认信息应尽量保留使用者原话。

### 15. uncertainty

目前无法从图片确认的事项。

最低要求：真实列出限制，例如地点、身份、文字内容、时间、天气、滤镜、材质；若图片确实没有需要保留的疑点，写"本图未发现需特别保留的不确定项"，但必须先检查。不得用套话填满该项。

### 16. title

适合 Archive 的图片标题。

最低要求：1–5 个英文单词（长度已适度放宽），取自画面本身，符合现有 Archive 语气；
不得使用设备文件名；不得与现有条目标题重复。标题未定稿时明确标注"暂定"。

## 4. 观察与推论的写法

- 观察：可直接在像素中核对，例如位置、比例、颜色、文字是否可见、遮挡关系、实测 hex。
- 推论：对风格、动机、情绪、地点、人物关系的判断，用"推测""可能""像是"等词。
- 不要把推论写成事实句；也不要把事实段写成纯感受。
- 画面没有呈现的声音、气味、天气原因、人物关系、拍摄动机，一律不得补写。
- 使用者确认过的信息可以写进 `echoes.confirmed`，并注明来自使用者记录，而不是图像证据。
- 不确定的事项不得用常识补齐。会影响归档判断的疑点（地点、身份、文字含义）保留在
  `uncertainty`，必要时请使用者确认；不要为了让分析完整而编造答案。

## 4.1 历史分析恢复规则

- 先保存原始分析，再做映射。原文保存到 `docs/analysis-recovery/original/<id>.txt`。
- 原文文件只摘录该图片对应的用户可见助手报告；不包含内部推理、工具日志或后续改写。
- 映射只调整字段位置、字段名称、嵌套类型和必要标点；不重新观察图片，不改写视觉结论。
- 原始分析的独特描述必须保留。不得用固定模板替换颜色、构图、材质或交互判断。
- 顶层 `title`、`accent`、`category`、`echoes` 以当前条目为准。原文与当前元数据冲突时，
  写入 `mappingNotes` 并等待所有者确认，不借标准化顺手改标题、分类或联想。
- 若当前条目完全没有 `echoes`，原文明确列出的 AI 联想只能恢复到
  `proposedPatch.echoes.candidates`；`confirmed` 保持空数组，不得升级为使用者确认。
- 原文未覆盖某字段时按 2.1 标记待补充，不根据 `note`、标签或常识补写。
- 同一图片存在多个历史版本时，优先选择最接近当次归档、字段最完整且可由消息 ID 验证的版本。
- 只有原文、标准化草案和映射清单三者都能对应到同一 `id` 与图片路径时，才可进入正式写入。

## 5. Visual DNA 的使用

五个类别是当前工作分类，不是永久固定标签：

- NATURE：自然物、植物、地貌、动物、天气是主要视觉结构。
- MEMORY：地点、旧物、时间感、可辨认的个人记忆场景。
- STRANGE：反常、错位、超现实、令人停一下的异常关系。
- COLOR：颜色本身主导画面与观看感受。
- DREAM：朦胧、漂浮、失焦、超现实的柔和氛围。

选择时以画面证据为准，不以拍摄地点或使用者经历代替视觉判断。允许"主类 + 次类"的分析，但 Archive 的 `category` 只保留一个主类。

## 6. Echoes 的处理

- AI 主动想到的电影、绘画、音乐、地点、物件，先进 `candidates`。
- 使用者明确确认的内容才进 `confirmed`。
- 地点、植物/建筑识别、拍摄者身份，本质上都是可确认信息；没有确认就只能是候选。
- `confirmed` 可以包含使用者的个人记忆；`candidates` 不得伪装成个人记忆。
- 两类都允许为空数组；不要为了填满而制造联想。

## 7. 正式输出格式

报告使用中文；每张图片独立成节，按下列顺序写完整 16 项：

```markdown
## Title（DNA / category）

![Title](/absolute/path/to/image.jpg)

- **content**：
- **composition**：
- **color**：
- **typography**：
- **texture**：
- **material**：
- **spatialDepth**：
- **hierarchy**：
- **mood**：
- **visualStyle**：
- **interaction**：
- **dna**：
- **accent**：
- **echoes**：
- **uncertainty**：
- **title**：
```

要求：

- 图片用本地绝对路径内嵌，使用者不必另开侧边栏。
- 先写观察，再写推测；推测句要能被识别。
- 每轮固定 3 张，逐张完成；上一张的分析与检查结束后才开始下一张。批次报告仍需说明
  每张图的 DNA 与标题。
- 若该图是新条目，另附"Archive 映射"：`id`、`title`、`date`、`source`、`medium`、`category`、`note`、`image`、`accent`、`tags`、`echoes`、`analysis`。
- `analysis` 保存 13 个分析字段；`title`、`accent`、`echoes` 使用条目顶层现有字段，不重复写入。
- `note` 沿用现有 Archive 的单句风格；完整分析不压缩成 `note`。

## 8. 质量检查

### 8.1 可自动检查的部分

运行：

```bash
python3 scripts/check_archive.py
```

它检查数据结构层面：JSON 可解析、必需字段与类型、取色格式、日期格式、id 唯一、图片存在、
无孤儿图片、文件名与 id 对应、标题词数、echoes 数组类型，以及 `analysis` 的 13 个字段是否
存在、是否为非空字符串、是否短到明显不足以达到要求。

旧条目没有 `analysis` 属于已知历史状态，默认只统计覆盖数，不报错。若要把缺失视为错误，
运行 `python3 scripts/check_archive.py --strict-analysis`。

脚本只能检查形式；分析深度仍按 8.2 逐图检查。

历史恢复的样本和批次另运行：

```bash
python3 scripts/check_analysis_recovery.py
```

它检查样本清单、原文文件哈希、13 个字段、顶层标题/强调色/echoes 对应关系、图片路径和
未决事项。脚本通过只表示可以审阅，不表示项目所有者已经接受分析判断。

### 8.2 内容质量检查（逐图、人工与模型自检）

以下阈值是本规范的验收标准，用来防止空泛输出；历史恢复逐条通过后同样适用。

每项都要有可指认的依据，不能只勾选"已写"：

- [ ] 16 个字段齐备且顺序正确，没有用一个词或"无"敷衍整个字段。
- [ ] `content` 至少列出 3 个可核对元素，并说明关系。
- [ ] `composition` 至少有两组空间关系，并指出负空间/遮挡/非主体区域；不是"居中构图"式短语。
- [ ] `color` 有主色、辅助色、强调色的角色区分，并解释颜色如何影响层级或情绪。
- [ ] `color` 与 `accent` 至少各含一个来自本图的实测值，且 `accent` 的取样位置写清楚。
- [ ] `typography` 明确回答有字/无字；有字无法辨认时写"不可辨"，不猜内容。
- [ ] `texture` 覆盖至少两个区域或尺度。
- [ ] `material` 至少两种可辨认材质，或明确说明无法确认。
- [ ] `spatialDepth` 至少三层，或明确说明画面被压平；机位判断如果存在，标为推测。
- [ ] `hierarchy` 是有序的注意力路径，每条都有视觉原因。
- [ ] `mood` 写成"视觉证据 → 情绪效果"，不是单个形容词。
- [ ] `visualStyle` 至少两个形式特征；风格来源的猜测有标记。
- [ ] `interaction` 为 1–3 个与画面结构相关的具体方案。
- [ ] `dna` 引用画面证据；没有强行归类。
- [ ] `echoes` 的 `candidates` 与 `confirmed` 没有混用；确认项可追溯到使用者。
- [ ] `uncertainty` 列出真实限制，不是空话。
- [ ] `title` 为 1–5 个英文单词、非设备文件名、不与现有标题重复。
- [ ] 报告为中文；观察与推论分开；没有补写画面外信息。
- [ ] 历史恢复条目有原始文件、消息来源、原文 SHA-256 和映射版本。
- [ ] 原始分析中的每个有效判断都能在标准化结果或 `mappingNotes` 中找到去向。

### 8.3 需要使用者确认的部分

以下属于主观判断，自动化只能检查形式，最终由项目所有者确认：

- DNA 主类是否贴合。
- 标题是否合适。

- 情绪与风格判断是否接受。
- 分析内容是否准确、是否达到可写入 Archive 的标准。

## 9. 固定执行流程

1. 读取 `AGENTS.md` 和本规范。
2. 检查现有 Archive，辨识已经归档的图片。
3. 确认待处理图片尚未归档（用感知哈希，裁掉黑边后比较）；已归档图片直接跳过，不重新分析。
4. 一次只读取一张图片。
5. 完成该图片的完整 16 项分析。
6. 按第 8 节检查分析。
7. 分析通过后，才建立或更新 Archive 数据，并把完整分析写入 `analysis` 对象。
8. 校验图片、JSON 与页面显示一致。
9. 回报完成的工作与未解决问题。

每张图片必须先完成分析，再进入下一张。不得并行读取多张图片，不得因批次导入而省略分析，不得在分析未完成时先写正式数据。

如果候选图与 Archive 中的图片是同一张（包括裁剪、去水印、重新导出等版本），按重复处理并跳过；不要因为文件名不同就重新分析。

不得归档使用者本人出现的照片，包括自拍和合影；选图时直接跳过，无法判断时先询问。

工具异常处理：

- 出现 `No tool output found for tool call ...`、`413 Payload Too Large` 或类似状态错误时，立即停止相关操作。
- 不要连续重试同一调用。
- 报告失败；若怀疑对话状态损坏，建议新开会话，而不是继续在同一状态里反复操作。
- 未完成的工作不得写成完成。

## 9.1 历史补录的逐条事务

每处理一条历史分析，必须按以下顺序完成：

1. 用当前 `id`、标题和图片路径锁定唯一 Archive 条目。
2. 在历史记录中找到该条目的当次用户可见分析，记录 session ID、message ID 与时间。
3. 将对应原文单独保存到 `docs/analysis-recovery/original/<id>.txt`，计算 SHA-256。
4. 先生成 `docs/analysis-recovery/normalized/<id>.json`，只做 16 项映射。
5. 对比原文与标准化结果，列出所有改写、类型变化、待补充和元数据冲突。
6. 运行 `python3 scripts/check_analysis_recovery.py --entry <id>`。
7. 写入 `data/entries.json` 前，再验证该条图片仍存在、内容对应同一画面、没有重复 id。
8. 单条 JSON 解析和恢复检查通过后，才追加该条的 `analysis` 与 `analysisSource`。
9. 立即运行 `python3 scripts/check_archive.py --strict-analysis`；通过后才进入下一条。

任何工具报错、载荷错误或无法验证内容时，停止当前条目，保留已经保存的原文与草案；不得继续
批量写入，也不得把失败条目计为完成。

## 13. 完整分析参考案例：Night Sparks

本案例用于展示 16 项分析应达到的深度，不修改 Archive 条目，也不代表要对已归档图片做例行重析。

原图：`images/fireworks-night.jpg`（1600×900），归档日期 2026-07-25，`category` 为 `dream`。

- **content**：夜空中有多组烟花同时炸开：中央偏左一组最大，右中一组次大，左上、左下、右下还有更小的花束；画面底部与左侧是树冠剪影，底边约略可见少量地面光点。没有人物、建筑轮廓或可读标识。
- **composition**：横幅 16:9。最大的两束烟花占据上半部，中央偏左与右中形成双主体；树冠的黑色剪影沿底边与左缘压住画面，像一条暗色底座；下半部若干烟花被树遮住一部分。视线从中央最大花束向右移动，再落回底部光点。上半部大片黑天是负空间，让各束烟花之间保持距离。
- **color**：背景不是纯黑：天空顶部实测 **#090B12**，树冠 **#040403**；火花以暖白为主，亮部平均约 **#C8BAB9**，峰值可到 #FFFFFF；低处几组带粉紫 **#C9B0B7**，并有少量橙黄光点。视觉关系是小面积高亮火花对大面积近黑背景，形成强对比；粉紫只出现在低处，形成第二层色温。
- **typography**：画面中无可见文字、数字或标识。
- **texture**：火花是细密、断续的颗粒线，越靠外越松散；天空几乎没有纹理，只有轻微噪点；树冠是近黑剪影，边缘参差但看不到叶面细节。近处的光点较实，远处烟花更碎更软。
- **material**：可辨认的是夜空中的光与烟、前景树叶剪影；底部有小面积灯光。没有足够信息确认建筑、水面或地表的材质。
- **spatialDepth**：前景是树冠剪影（最暗、遮挡烟花），中景是两束主烟花，远景是更小更碎的花束与暗天。画面没有地平线，深度主要来自烟花尺度、遮挡与亮度；后层烟雾让远处火花显得更散。
- **hierarchy**：1）中央偏左最大花束（面积最大、亮度最高）→ 2）右中第二束（次大、边缘略软）→ 3）底部沿树分布的粉紫与白色碎光 → 4）黑色树冠。树冠面积最大但亮度最低，因此不抢第一眼。
- **mood**：黑底上的密集爆裂与光点带来庆典、开阔、短暂的感觉；树冠压低底部，让人像站在树下或远处观看，热闹中带一点距离感。画面没有人群、声音或地点标识，因此不能判断现场是否拥挤。
- **visualStyle**：夜间活动摄影，强对比、暖白高光、轻微长曝光/拖尾感；色彩被压到近黑，只有火花发亮。细节偏柔，像远距离或手持拍摄，不能确认具体设备与参数。
- **interaction**：1）前景树冠与烟花分层视差，滚动时树先动、烟花后动；2）火花做极慢的闪烁与微弱拖尾，不改变构图；3）悬停时让底部粉紫碎光略增强，强调第二层色彩。
- **dna**：主类 **DREAM**（夜景、漂浮的光、短暂爆裂的梦境感）；可带 **COLOR** 次类（近黑背景与暖白/粉紫的对比）。Archive 的 `category` 只记录为 `dream`。
- **accent**：**#201B21**（取样于中央烟花下方的烟雾与暗部；实测存在约 6,565 个接近该值的像素）。更深的天空是 #090B12。火花本身的暖白 #C8BAB9 更适合作为辅助色，不适合做卡片强调色。
- **echoes**：`candidates`：夏夜庆典、电影片头式的烟花场景（AI 联想，未确认）；`confirmed`：大稻埕夏日烟花祭（来自使用者已确认记录，不是图像可见信息）。
- **uncertainty**：图像本身看不出地点、日期与是否为同一瞬间的连续拍摄；多组烟花是同步绽放还是长曝光/叠加结果，无法确认；没有人物或地标；标题沿用现有条目，不重新命名。
- **title**：Night Sparks（2 个英文词，沿用现有标题）。
